*pi-nvim-protocol* *pi-nvim-jsonl*

Pi–Neovim JSONL Protocol

Transport and framing                              *pi-nvim-protocol-transport*

The Neovim plugin owns and listens on a Unix-domain socket and supplies its
path to Pi as `PI_NVIM_SOCKET`. The Pi extension connects to that path. Messages
are UTF-8 JSON objects, one per line, terminated by `\n`. A JSON object may
span socket chunks; a chunk may contain multiple messages. There is no
protocol message-size limit.

Every request has a non-empty string or numeric `id` and a `type`. The
extension sends one response for each valid-ID request after the operation
succeeds or fails. The response echoes the ID. Messages are processed in stream
order on each connection. There are no unsolicited messages and no version
handshake.

Requests and responses                               *pi-nvim-protocol-messages*

Submit a prompt                                    *pi-nvim-protocol-submit*

  { "id": "req-1", "type": "submit_prompt", "prompt": "Explain this function" }

`prompt` is the complete user prompt. The extension starts a turn immediately
when Pi is idle. If Pi is busy, it queues the prompt as a follow-up.

Edit a buffer                                      *pi-nvim-protocol-edit*

  {
    "id": "pi-3",
    "type": "edit_buffer",
    "path": "src/main.lua",
    "operation": {
      "start_row": 0,
      "start_col": 0,
      "end_row": 0,
      "end_col": 5,
      "replacement": ["local"]
    }
  }

Pi sends this request to Neovim. Each invocation edits exactly one buffer. Use
a non-empty `path` to target a named buffer; its file must exist and already
be open in Neovim. Relative paths are resolved from the Pi session working
directory. Use `path: null` only for the remembered source buffer that was
active before entering the Pi window. It must still be valid, unnamed, and
have normal `buftype`; the Pi buffer is never an eligible target. Missing
files are not created.

`operation` has `start_row`, `start_col`, `end_row`, `end_col`, and
`replacement`. Each tool call performs exactly one edit operation on exactly
one buffer; make separate calls for multiple edits. Rows are zero-based;
columns are zero-based byte offsets, matching Neovim's buffer text API. The
range is half-open, from the start position up to but not including the end.
`replacement` is an array of UTF-8 strings, one per resulting line. An empty
range inserts; an empty replacement array deletes the range. Out-of-bounds
ranges fail. Byte offsets are not specially checked for UTF-8 code-point
boundaries.

Edits change only Neovim's in-memory buffer; they do not write to disk. The
tool is intended only for edits the user explicitly requested. Success returns
an empty object.

Insert a visual selection                        *pi-nvim-protocol-selection*

  {
    "id": "req-2",
    "type": "insert_selection",
    "text": "selected text",
    "selection": {
      "buffer_id": 7,
      "path": "src/main.lua",
      "buffer_name": "main.lua",
      "start_line": 3,
      "start_col": 1,
      "end_line": 4,
      "end_col": 9,
      "selection_type": "line"
    }
  }

`text` is inserted at the current Pi input-editor cursor position, preserving
existing editor content. This request does not submit the editor contents.
`selection` contains the source buffer identity (`buffer_id`), path (nullable
when unavailable), buffer name, 1-based start/end line and column, and
selection type (`character`, `line`, or `block`). Block selections require no
additional corner semantics.

Success                                           *pi-nvim-protocol-success*

  { "id": "req-1", "ok": true, "result": {} }

Failure                                           *pi-nvim-protocol-failure*

  { "id": "req-2", "ok": false, "error": "Pi input editor is unavailable" }

The receiver reports validation and operation failures this way, including
buffer-edit range and target errors. For malformed JSON, it
sends a failure when it can recover a valid ID from the input line. It closes
neither the Pi process nor the connection merely because a request fails. A
request without a recoverable ID cannot receive a correlated response.

Operation completion                                *pi-nvim-protocol-completion*

A success response means the extension API call completed successfully:
prompt submission was accepted by Pi (including queueing a follow-up), or
selection text was pasted into the editor, or buffer edits were applied in
memory. A failure response communicates that the requested operation could not
be completed. Responses are serialized
in request order per connection.
